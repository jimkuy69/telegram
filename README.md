# Telegram Control Studio

Local-first Windows desktop application for consent-first Telegram account and campaign management.

## Current status

- Phase 0: research/compliance completed outside this repository; implementation constraints are recorded in the approved plan.
- Phase 1: WPF solution skeleton, Core domain types, SQLite initialization boundary, dashboard shell, and secret-redaction test added.
- Phase 2: TDLib native loader/adapter and the Windows x64 artifact-build workflow are present. The native package is generated by GitHub Actions and must be downloaded and verified before packaging; it is not committed to the source tree.
- Phase 0 send safety: persisted test mode (on by default), per-recipient allowlist, and an emergency stop (kill switch) are enforced before any TDLib transmission.
- Phase 1 library split: `Core` and `Infrastructure` are UI-agnostic net8.0 libraries consumed by the WPF app through the shared `StudioHost` bootstrap.
- Session lock: each TDLib session is guarded by a named mutex per account, so two instances of the app can never open the same session database at once.
- Queue auto-runner: once an account is signed in inside the app, confirmed (`Queued`) jobs and jobs whose flood-wait cooldown has elapsed are sent by a background loop without another click. See [Queue auto-runner](#queue-auto-runner).
- Latest CI evidence: managed build/test, dependency vulnerability scan, and Gitleaks passed on Commit `e2accb6`. Native TDLib runtime remains a separate artifact-gated check.
- Live evidence (2026-10-31): the desktop runner sent one real message to the signed-in account's own Saved Messages while the app was driven against a copy of the local database (`LIVE_AUTO_RUN_OK`). Campaign consent, confirmation, allowlist, and manual-acceptance gates still apply to every other recipient; bulk sending to real contacts has not been performed.
- History: a Blazor web host and Telegram owner bot (phases 1–3) were built, live-verified, then removed on 2026-10-31 to keep the product desktop-only. They remain recoverable from git history up to commit `8ad4751`.

## Download the latest Windows installer

1. Open the repository's [Actions page](https://github.com/jimkuy69/telegram/actions).
2. Open the latest successful **Windows installer release** run.
3. In **Artifacts**, download `TelegramControlStudio-installer-main`.
4. Extract the ZIP and run `TelegramControlStudio-installer.exe`.
5. Keep the installer ZIP and its `release-manifest.json` together for audit/reference.

The artifact is retained by GitHub Actions for 90 days. The installer is self-contained for Windows x64; user data is stored under `%LOCALAPPDATA%\\TelegramControlStudio\\`, not in the install directory.

This build is suitable for local foundation testing. Live Telegram sending, invite operations, clean-machine upgrade validation, and manual pilot acceptance still require the explicit gates in [DEVELOPMENT-PLAN-CHECKLIST.md](DEVELOPMENT-PLAN-CHECKLIST.md).

## Library layout

| Project | Target | Contents |
|---|---|---|
| `TelegramControlStudio.Core` | net8.0, no WPF/Windows dependencies | domain records, pure policies (send safety, consent state, paging, job status), TDLib JSON parsers, import/export |
| `TelegramControlStudio.Infrastructure` | net8.0 | SQLite persistence and migrations, TDLib transport/native loader, DPAPI secret storage, `StudioHost` bootstrap |
| `TelegramControlStudio.App` | net8.0-windows (WPF) | desktop host; the only UI project |

The app starts through the shared bootstrap:

```csharp
await using var host = await StudioHost.StartAsync();          // resolves the DB, runs migrations, owns TDLib clients
var databasePath = host.DatabasePath;
```

`StudioHost.StartAsync(new StudioOptions(path))` accepts an explicit database path, and `StudioOptions.CreateDefault()` honors `TELEGRAM_CONTROL_STUDIO_DB`. UI-agnostic rules live in Core: `SendSafetyPolicy`, `ContactConsentPolicy`, `PagingPolicy`, `JobAggregateStatusPolicy`.

Every TDLib session is protected by `TdLibSessionLock`, a named mutex per account (`Local\TCS-TDLibSession-{accountId}`). The app acquires it before connecting a session and holds it for the app's lifetime, which prevents a second app instance from opening the same TDLib session database.

## Send safety (Phase 0)

All outbound messages pass through one choke point (`TdLibMessageSendService`) that evaluates `SendSafetyPolicy` before building a TDLib request:

| Control | Default | Behavior |
|---|---|---|
| Test mode | ON | Only allowlisted Telegram user IDs may receive messages; everyone else is skipped with the reason recorded on the job item. |
| Allowlist | Empty | With test mode on and an empty allowlist, nothing can be sent. |
| Kill switch | Off | Blocks every send immediately, pauses running jobs, and logs `KillSwitchEngaged`. Sending stays blocked until it is cleared explicitly. |

- Settings are stored in the single-row `send_safety_settings` table, so they survive restarts and are the durable source of truth.
- The kill switch is exposed in the main window header, the Queue window banner, and Settings; queued jobs can be confirmed or resumed only while it is clear.
- A block pauses the job (item returns to `Queued`) so work resumes after the switch is cleared; a test-mode skip marks the item `Skipped` and pauses the job only when nothing was sent.
- Enforcement is defensive depth: the campaign runner and consent campaign service check the policy per recipient, and the send service re-checks before transmission.
- For isolated verification, set `TELEGRAM_CONTROL_STUDIO_DB` to a database file path to run against a copy instead of `%LOCALAPPDATA%\TelegramControlStudio\telegram-control-studio.db`.

## Queue auto-runner

`CampaignAutoRunner` runs on a background loop inside the desktop app (one tick every 15 seconds, `App.OnStartup`). It only acts on accounts whose TDLib session is connected in that process — signing in is still a human action, and nothing is sent before it.

| Rule | Behavior |
|---|---|
| Eligible jobs | `Queued` jobs (already confirmed by a human in the Queue window) and `WaitingForFloodWait` jobs whose cooldown has elapsed, oldest first, and only when `message_text` is not blank. |
| Never auto-started | `WaitingForConfirmation`, `Draft`, `Paused`, and terminal jobs. A pause is treated as an instruction, not a failure. |
| Claims | `JobRepository.TryClaimAsync` flips the job to `Running` in one atomic statement, and `JobInFlightGate` blocks the loop while the Queue window or Campaign wizard is driving the same job, so no recipient is ever double-sent. |
| Stops | The send loop re-reads the job status before each recipient, so pressing หยุดชั่วคราว or ยกเลิก in the Queue window stops an auto-run within one item. The kill switch pauses every item and the loop skips ticks while it is engaged. |
| Flood wait | A `FLOOD_WAIT_n` response parks the job until `flood_wait_until`; the next eligible tick resumes it, so long campaigns continue unattended. |
| Surface | The main-window header badge shows `AUTO-RUN: พร้อม (n)`, `กำลังส่ง n`, `รอเข้าสู่ระบบ`, or `หยุดฉุกเฉิน`. |

Jobs finished by the loop are logged as `AutoRunFinished`, failures as `AutoRunFailed`, and tick failures as `AutoRunTickFailed` in the activity log.

## Security boundary

Never commit API hashes, OTPs, 2FA passwords, TDLib sessions, local databases, or native binaries. The application is designed to use Windows-protected secret storage and local data only.
