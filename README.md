# Telegram Control Studio

Local-first Windows desktop foundation for consent-first Telegram account and campaign management.

## Current status

- Phase 0: research/compliance completed outside this repository; implementation constraints are recorded in the approved plan.
- Phase 1: WPF solution skeleton, Core domain types, SQLite initialization boundary, dashboard shell, and secret-redaction test added.
- Phase 2: TDLib native loader/adapter and the Windows x64 artifact-build workflow are present. The native package is generated by GitHub Actions and must be downloaded and verified before packaging; it is not committed to the source tree. Live Telegram authentication remains pending.
- Phase 0 send safety: persisted test mode (on by default), per-recipient allowlist, and an emergency stop (kill switch) are enforced before any TDLib transmission.
- Phase 1 library split: `Core` and `Infrastructure` are UI-agnostic net8.0 libraries; the WPF app and the web host share `StudioHost` and the same policies.
- Phase 1 web host: ASP.NET Core 8 + Blazor Server surface (dashboard, recipients, compose, queue, settings) that plans jobs and controls send safety against the same local database. Real sending still happens in the desktop app.
- Phase 2 web access: Telegram Login Widget via the owner's bot, invite-only friend accounts (`app_users`, `invites`), owner/friend route gating, and an owner bot remote (`/status`, `/approve`, `/cancel`, `/kill`, `/invite`). Friends can only see their own consent status and opt in/out.
- Latest CI evidence: managed build/test, dependency vulnerability scan, and Gitleaks passed on Commit `e2accb6`. Native TDLib runtime remains a separate artifact-gated check. These results do not prove live Telegram E2E.
- Account/session, messaging, invitation, and real Telegram calls remain behind TDLib runtime, consent, confirmation, and manual-acceptance gates; no live Telegram E2E is claimed.

## Download the latest Windows installer

1. Open the repository's [Actions page](https://github.com/jimkuy69/telegram/actions).
2. Open the latest successful **Windows installer release** run.
3. In **Artifacts**, download `TelegramControlStudio-installer-main`.
4. Extract the ZIP and run `TelegramControlStudio-installer.exe`.
5. Keep the installer ZIP and its `release-manifest.json` together for audit/reference.

The artifact is retained by GitHub Actions for 90 days. The installer is self-contained for Windows x64; user data is stored under `%LOCALAPPDATA%\\TelegramControlStudio\\`, not in the install directory.

This build is suitable for local foundation testing. Live Telegram sending, invite operations, clean-machine upgrade validation, and manual pilot acceptance still require the explicit gates in [DEVELOPMENT-PLAN-CHECKLIST.md](DEVELOPMENT-PLAN-CHECKLIST.md).

## Library layout

| Project | Target | Contents |
|---|---|---|
| `TelegramControlStudio.Core` | net8.0, no WPF/Windows dependencies | domain records, pure policies (send safety, consent state, paging, job status), TDLib JSON parsers, import/export |
| `TelegramControlStudio.Infrastructure` | net8.0 | SQLite persistence and migrations, TDLib transport/native loader, DPAPI secret storage, `StudioHost` bootstrap |
| `TelegramControlStudio.App` | net8.0-windows (WPF) | desktop host; the only WPF-specific project |
| `TelegramControlStudio.Web` | net8.0 (ASP.NET Core, Blazor Server) | local web host: dashboard, recipients, compose, queue, safety settings |

Any additional host starts the same way:

```csharp
await using var host = await StudioHost.StartAsync();          // resolves the DB, runs migrations, owns TDLib clients
var databasePath = host.DatabasePath;
```

`StudioHost.StartAsync(new StudioOptions(path))` accepts an explicit database path, and `StudioOptions.CreateDefault()` honors `TELEGRAM_CONTROL_STUDIO_DB`. UI-agnostic rules shared by hosts live in Core: `SendSafetyPolicy`, `ContactConsentPolicy`, `PagingPolicy`, `JobAggregateStatusPolicy`.

## Web host (Blazor Server)

```powershell
dotnet run --project src/TelegramControlStudio.Web --urls http://127.0.0.1:5199
```

or use the `http` launch profile (same URL) from an IDE.

| Screen | Purpose |
|---|---|
| แดชบอร์ด | account, consent counts, job counts, recent activity (owner) |
| ผู้รับ | search/filter by consent state, explicit selection with paging (owner) |
| เขียนข้อความ | message + link + preview, creates a job in `WaitingForConfirmation` (owner) |
| คิวงาน | confirm a job into `Queued`, cancel, engage/clear the emergency stop (owner) |
| ผู้ใช้และคำเชิญ | invite links, user roles, block/unblock, public base URL (owner) |
| สถานะของฉัน | own consent status with opt-in / opt-out (every signed-in user) |
| ตั้งค่า | test mode, allowlist, kill switch, account list, bot commands, machine info (owner) |

- The host is bound to localhost and requires login: Telegram Login Widget via the owner's own bot, verified server-side (`TelegramLoginVerifier`), then an HttpOnly `tcs_auth` cookie. Everyone else joins through a single-use invite link (`/invite/{code}`).
- The first successful login on an empty `app_users` table becomes **Owner**; all other accounts are **Friend** until an owner invite grants otherwise.
- Bot token setup: create a bot with @BotFather, run `/setdomain <host>`, then paste the token on `/login`. The token is stored with Windows DPAPI in `app_secrets`; never commit it.
- Token rotation: revoke with @BotFather `/revoke`, then open `/login?setup=reset`. A stored token that still works cannot be replaced (the page answers `already`); once it fails against Telegram, replacing it needs the previous token as proof — or no accounts at all.
- HttpClient request logging is filtered to `Warning` because the Bot API carries the token in the request path; keep that filter if you change the logging configuration.
- The owner bot is a remote control (`/status`, `/jobs`, `/job`, `/approve`, `/cancel`, `/testmode`, `/kill`, `/invite`, `/users`); friends can only use `/me`, `/optin`, `/optout`. The bot only plans and gates work too — sending stays in the desktop app.
- If the host is exposed through a Cloudflare Tunnel, put Cloudflare Access in front of it as well; the app's own login is the second layer, not a replacement.
- The web host plans and gates work; TDLib login and every real send stay in the desktop app. A confirmed job waits for the desktop runner.
- Job creation reuses the desktop idempotency rules, so re-submitting the same recipients/message returns the existing job.
- Every page shows the current safety state; cancelling or confirming is logged as `JobQueuedWeb`, `JobCancelledWeb`, `EmergencyStopEngaged`, `KillSwitchCleared`, `SendSafetyUpdated`.
- Use `TELEGRAM_CONTROL_STUDIO_DB` to point the host at a copy of the database when testing.

## Send safety (Phase 0)

All outbound messages pass through one choke point (`TdLibMessageSendService`) that evaluates `SendSafetyPolicy` before building a TDLib request:

| Control | Default | Behavior |
|---|---|---|
| Test mode | ON | Only allowlisted Telegram user IDs may receive messages; everyone else is skipped with the reason recorded on the job item. |
| Allowlist | Empty | With test mode on and an empty allowlist, nothing can be sent. |
| Kill switch | Off | Blocks every send immediately, pauses running jobs, and logs `KillSwitchEngaged`. Sending stays blocked until it is cleared explicitly. |

- Settings are stored in the single-row `send_safety_settings` table, so they survive restarts and are the durable source of truth.
- The kill switch is exposed in the main window header, the Queue window banner, and Settings; queued jobs can be confirmed or resumed only while it is clear.
- A block pauses the job (item returns to `Queued`) so work resumes after the switch is cleared; a test-mode skip marks the item `Skipped` and pauses the job only when nothing was sent.
- Enforcement is defensive depth: the campaign runner and consent campaign service check the policy per recipient, and the send service re-checks before transmission.
- For isolated verification, set `TELEGRAM_CONTROL_STUDIO_DB` to a database file path to run against a copy instead of `%LOCALAPPDATA%\TelegramControlStudio\telegram-control-studio.db`.

## Security boundary

Never commit API hashes, OTPs, 2FA passwords, TDLib sessions, local databases, or native binaries. The application is designed to use Windows-protected secret storage and local data only.
